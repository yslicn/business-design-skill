# 内容报告契约（v3）

用于写作、独立评审及 MD→DOCX 交付。它取代默认流程中的页面模板契约。

## 两项强制交付门

1. **有效正文字数 10,000–15,000，含上下限。** 从 MD 可见正文计算：一个中文汉字计一字，英文/数字词计一词。执行摘要、分析段落、正文表格计入；标题、目录、参考文献/来源清单、附录、脚注、图中文字/图注、代码、链接地址与证据编号不计入。完全重复的正文块只计一次；语义重复由 Reviewer 剔除后重查。目录/附录/来源部分使用明确 Markdown 标题。禁止填充无关背景和同义复述。
2. **正文必须同时有可视化与数据分析。** 机器最低检查：至少一个实际嵌入正文的计划展项 PNG（能匹配 exhibit_plan 和 exhibits_manifest，文件有效）；至少一处带有效台账证据编号的量化正文/数据表，或带有效证据引用及数值数据的量化展项。重复图片不算新增展项，附录图片不充当正文图表，Logo/装饰图不能满足要求。机器最低数量不是写作目标：市场比较、客户选择和盈利逻辑等关键判断应按内容配置图表；原有典型 8–14 展项指导保留。

Reviewer 必须逐章判断图表是否承载真实分析、关键数据是否解释单位/期间/口径、数字是否支持具体结论。不能只写年份、证据序号或评分就冒充经营数据；不能用流程图替代量化内容。估算须标明依据和假设，缺数据不编造。机器检查不证明图表语义或数据真实性。

执行 `python3 scripts/check_content_gates.py --project <project>` 可提前定位缺口；最终交付检查重新计算当前 MD，不接受手填“字数达标”。导出器仍可生成草稿，只有通过硬门才能标记正式交付通过。

## 正文组织

先写执行摘要：回答管理层应选择什么、放弃什么、为什么现在、靠什么赚钱、下一步验证什么。摘要是正文结论的综合，不是机械拼接七章 key_message。正文七章依照 VDBD 保持决策链，每章标题可以用“章节名称：核心判断”，二三级标题围绕具体论点展开。

每个重要建议需要足够的论证：所依据的事实与来源、如何从事实得到结论、相比替代选项的取舍、对本企业的影响、成立条件与执行办法。以连贯段落为主；表格用于真实比较、权重评分、经济测算或风险映射，不能把所有分析写成单元格清单。关键表格前后解释比较结果为什么改变决策。

七章至少解决：

| 章节 | 必须回答的决策问题 |
|---|---|
| 市场扫描 | 价值从哪里流向哪里，变化的机制是什么，哪些变化与本企业有关？ |
| 客户选择 | 为什么选这类客户/环节，为什么其他高利润机会未必适合，评分依赖什么假设？ |
| 价值主张 | 客户为何切换，替代方案是什么，差异化如何被客户验证？ |
| 盈利模式 | 谁为哪一单位价值付费，价格和合同怎样形成利润，什么变量会击穿经济性？ |
| 活动范围 | 自建、合作、外包、退出如何取舍，资源如何分配，业务边界如何兑现？ |
| 战略控制 | 控制哪个稀缺环节，如何阻止价值被客户、供应商或竞对夺走？ |
| 风险管理 | 什么会推翻设计，领先信号/止损条件是什么，由谁何时验证和应对？ |

附实施顺序和验证计划（可并入相应章节），区分建议的责任角色与已承诺负责人；无资源数据时不要编造预算。附录放来源索引、假设/数据缺口、评分及测算明细。正文保留关键推理，不能以“详见附录”掩盖没有分析。有效正文必须为 10,000–15,000 字，篇幅达标之后仍须通过论证质量评审；同样禁止以"精炼"为名把研究报告中的量化论据压缩到只剩结论。

## 结构化章节骨架

每章按固定骨架组织，保证"必须回答的问题、观点、论据"三者显式完备（形式可调，要素不可缺）：

1. **必答决策问题**：开篇一句话列出本章要回答的决策问题（用上表），让读者知道这章解决什么。
2. **核心判断（观点）**：以可讨论、可证伪的判断句回答；判断必须公司特定，不能是行业通用口号。
3. **论据**：支撑判断的事实段落与表格，带 `[Exx]`/`[Axx]` 编号和具体数字（规模、增速、份额、价格、利润率、成本之一）。每个核心判断按类型提供充分证据，不设两条量化证据配额；量化结论有同口径量化依据；数据不足处显式记录数据缺口，不得以定性形容词代替。
4. **论证**：从事实到判断的推理——机制是什么、为何适用于本公司、因果链条的每步成立条件。
5. **取舍与边界**：替代方案、放弃理由、结论逆转条件。

执行摘要对每个结论只给判断与一句最强论据，完整论据留在对应章节；摘要中的判断必须能在正文找到展开论证。信息密度的检验标准：研究报告与证据台账中"会改变判断权重"的事实，要么进入正文支撑论证，要么在正文说明为何不影响结论；不允许无声丢弃。

## 图表与版面（Word 交付形态）

正文以论证为主，图表承载比较、结构与量化关系；两者不重复表达同一内容。

- **展项规划**：写作时为具备比较性或多维性的内容规划展项（典型七章报告 8–14 个）。`exhibit_plan.json` 与 MD/JSON 同步产出、同步变更，每个展项必有：观点式标题（action title，一句话判断，如"商品薄利、服务厚利：服务毛利率最高达商品分销的 8 倍"，禁止"图1：利润率数据"这类无观点标题）、类型、`source_refs` 证据编号、类型化数据。
- **确定性渲染**：展项 PNG 由 `scripts/render_report_exhibits.py` 统一渲染（9 类：环节评分、贡献构成、对标条形、漏斗、优先级矩阵、路线图、贡献桥、风险矩阵、价值迁移），风格统一：单色系+一个高亮色、直接数值标签、无 3D 无装饰。`segment_scores`/`contribution_stack` 直接读底稿 JSON，其余类型的数据必须逐字来自台账或底稿，渲染时校验 `source_refs` 真实存在。
- **MD 引用**：以 `![X01 观点式标题](exhibits/X01.png)` 紧邻其论证段落插入；图注即观点标题。导出器校验 MD 引用数与 DOCX 实际嵌入数一致，不一致不发布。
- **版式归属**：封面、目录域、页码、图注样式、表格样式由 `export_content_report.py` 统一处理，不在 MD 中手写任何版式。目录域与页码域在 Word/WPS 中更新一次后显示页码，此限制写入交付说明。
- **诚实性延伸到图表**：方向性测算的展项必须在图上标注"方向性/估计"注脚；unknown 不画成确定值；图表数字与正文、底稿矛盾按关键冲突处理。

## 从口号到论证的示例

弱：“聚焦高端客户，以技术创新打造差异化，提升盈利能力。”

合格的推理形态（仅示范结构，不是真实研究结论）：“建议先在既有客户中验证按设备收费的预防维护服务，再决定是否扩张到新行业。相比一次性硬件销售，这一路径可能更好地回收持续诊断成本；但前提是客户减少停机的收益高于年服务费、接入成本和误报损失。试点应同时记录付费意愿、每台设备的服务工时、续约意愿与实际回款；如果贡献利润仅在忽略现场服务成本后成立，应调整收费单位或停止扩张。”正式报告还须补入真实证据、竞争比较、企业能力与可复算测算，不能照抄此示例充当答案。

## MD、JSON 与证据一致性

MD 是正式叙述母稿；JSON 是结构化分析底稿。同一业务决策、数字或假设不得在两者出现不同版本。正文事实必须可回溯：优先引用证据台账 `[E01]`（含 `supporting_detail` 细节）；研究报告中有而台账未收录的事实可进正文，引用研究报告脚注号 `[Rxx]`，并在正文定稿前补录台账。事实一致性的标准是"可回溯到来源"，不是"必须先在 JSON 里"——但补录完成后，台账与正文必须互查一致。假设使用 `[A01]`，附录解析到来源标题、发布者、日期、URL 与适用口径；不能只给孤立编号。新增决策同步到 JSON；被修订的段落及相关底稿重新评审。DOCX 全量来自 MD。

不强求正文逐字包含 JSON 所有字符串，更不追加原始字段垃圾索引来骗取覆盖率。由人工确认重要结论、计算、反例、条件与证据没有遗漏；转换器只验证 MD→DOCX 的文本保留和源版本，不评价咨询质量。

## 独立内容评审

Architect 对七章逐章给出引用位置、评价与具体修订动作，再对以下七维打 1–5 分：

- 观点：1=通用口号；3=明确选择但依据单薄；5=公司特定、可检验、取舍明确。
- 论证：1=结论清单；3=有依据但因果跳步；5=事实→机制→判断→影响完整。
- 论据充分性：1=关键判断缺少直接相关支持；3=已有证据但口径、机制或反证不足；5=按判断类型获得充分支持：量化判断有同口径数据及可复算依据，客户流程、合同和能力边界有直接相关的一手材料，因果判断解释机制并考虑反证；改变判断权重的事实已用于论证或有排除理由，不按数量凑证据。评审时必须抽样对照研究报告对应章节检查利用率，不得只查编号可回溯。
- 证据：1=不可追溯；3=多数有据但关键口径不清；5=关键事实可核、估算可复算、局限透明。
- 取舍：1=只罗列机会；3=比较过候选；5=解释反例、机会成本、放弃理由及结论逆转条件。
- 经济性与执行：1=增长愿景；3=有机制但验证不具体；5=付费、成本、现金、敏感性及验证闭环明确。
- 阅读质量：1=字段/短句堆砌；3=可读但重复或跳跃；5=连贯长文、表格服务判断、摘要与正文一致。

每维至少 4 分、七章无重大缺陷才可 PASS；分数是带理由的人工判断，禁止脚本凭字数、关键词或字段覆盖率自动打分。虚构证据、核心观点无支撑、MD/JSON 关键冲突、盈利模式缺失、未披露的关键假设均直接 REVISE，不能用平均分抵消。受数据限制的方向性设计须明确边界，不得宣称已证明经济可行。

## DOCX 与交付检查

先运行 `render_report_exhibits.py` 渲染展项，再使用 `scripts/export_content_report.py` 转换已审 MD（封面信息用 `--title/--subtitle/--company/--date` 传入）。支持常规 Markdown 标题、段落、列表、表格、强调、链接、脚注与本地相对路径的展项 PNG；不要嵌入原始 HTML、分页指令、远程图片或未经验证的 LaTeX/复杂嵌套表格。长表可纵向分页和重复表头，不能丢行或将整张长表强制挤到一页。导出后实际渲染检查中文、表格单元格对应、段落顺序、链接目标、标题分页和正文可读性；有可用 documents/docx skill 时遵循其渲染工具，使用宿主提供的依赖。无渲染能力时标记 `docx_readability=PENDING` 并披露，不可宣称完整质量通过。

`report_manifest.json` 是转换结果，不是内容质量报告。独立评审与实际 DOCX 检查后，由主线程生成 `content_quality_report.json`：

### 中文渲染环境

若 bundled LibreOffice 渲染出现中文空白或方框，先检查该进程的字体配置。可在本次渲染命令设置 `FONTCONFIG_FILE` 指向宿主同一 LibreOffice bundle 内的 `Resources/fontconfig/fonts.conf`，并核实其中可访问的中文字体；不要更改全局配置或改用未经选择的桌面 LibreOffice。DOCX 的字体名可用导出器 `--font` 指定。转换成功或字符清单一致不代表渲染字体可用。

## 交付核验

见 reliability-and-handoff.md：quality 的 source_hashes 由实际文件计算，必要时用 artifact_paths 指向 report-vN 的 DOCX。存在展项时增加计划与 manifest 哈希，并核对 PNG。状态检查不再只相信 PASS 字段。定性一手证据可支撑合同/流程/能力判断，不强制凑两个数字。证据充分性统一按本文件的判断类型标准评审。
